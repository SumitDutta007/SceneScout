Promo Finder: picking promo clips from a microdrama screenplay

[Name · Roll no. · Branch]  ·  Problem 1  ·  Prototype + raw outputs: [GitHub link]

1. The problem, and why I picked it

Today an editor watches every episode of every show to find promo moments, and a new show ships every week. That cost grows with the catalogue and repeats forever, so it is the highest-leverage place to automate. The input also suits a tool unusually well: the scripts are timestamped cue by cue (camera, action, sound, dialogue with emotion tags), so the tool can return exact cut points an editor can act on, not vague suggestions. And the output is checkable, because every pick traces back to script lines.

2. Assumptions (where the brief was silent)

  • Script time ≈ final-cut time, within a second or two. Boundaries should be re-snapped on the video before cutting.
  • A promo is 20–60s. The hook sits in the first 3s of segment 1, the cliffhanger in the last ~4–6s. Stitched promos are 2–3 segments in story order. Cuts land only on a shot change, never mid-line.
  • The output is a shortlist for an editor (15 per show), not auto-posted clips. The goal is new-viewer acquisition, so early-episode entry points rank higher.
  • The title already reveals the twist ("He was a Duke"), so that reveal isn't a spoiler. Late-arc outcomes (ep 39+) are.
  • Every show arrives in this same script format.

3. How it works

Parse → legal cut points → score → generate candidates → (Claude judge) → select → order → quality flags → JSON / report / HTML viewer. One command: python -m promo_finder "data/<show>" --mode auto.

4. Scale and cost

  • Rules-only: 3.8s for a 50-episode show on a laptop. $0. No dependencies.
  • Hybrid: about 52 Claude calls per show (50 episode judges, 1 stitch, 1 rank), 6 in parallel. The show summary is prompt-cached across calls, and responses are disk-cached, so re-runs are free. Estimated at about 300k input and 250k output tokens per show: ≈$6 on Opus 5.5, ≈$0.15 on Haiku 5.5 (--model). The tool prints measured token use and cost per run. Nothing is latency-sensitive, so the Batch API would halve this.
  • Editor time: from watching ~100 min of footage per show to reviewing 15 shortlisted clips (≈20–30 min, my assumption).
  • What breaks at catalogue scale: main cast is already derived per show from dialogue counts, but speaker aliases (THE FORMER GROOM→Gerald) are a hand-made map; Claude could resolve them. Scripts that don't describe the music will score far lower on cliffhangers. A new script format needs a new parser.

5. How I know it's good, and where it fails

Honest status: every result here comes from the rule engine. The Claude layer is built and tested against a mocked API, but has not been run on real model output (no API key on this machine), so it is unproven.

Automated checks (9 tests, all passing): all 50 episodes parse; ep 6's missing scene end is repaired; no cut point splits a line; every candidate is 20–60s and in story order; the ep 3 proposal cliffhanger is found; Claude output with bad cue IDs or bad lengths is rejected.

Which to post first (my read): ① Ep 1 00:39.00–00:54.60 + 01:47.40–02:17.00 (sister takes the groom; the whole premise in 45s) → ② Ep 3 01:00.00–01:06.00 + 01:50.80–02:25.75 (dragged out, then a stranger kneels and proposes, answer withheld) → ③ Ep 12 00:56.80–01:09.50 + Ep 13 00:47.00–01:29.00 (gallows ultimatum into the barehanded crawl) → ④ Ep 36 02:36.50–03:20.75 ("their dead Duke is coming home") → ⑤ Ep 31 + 32 (hot iron). Hold ep 42–45 for retargeting: they spoil the arc. The tool generates all of these, but not all in its top 15, and I paired ③ by hand. That gap is exactly what the Claude judge and a gold set must close.

How "good" would be proven: (1) An editor logs the promos they actually cut for 5–10 past shows. --gold then reports precision@k and temporal IoU for every change. (2) Track the editor's weekly accept rate on new shows. (3) The real judge is promo performance: 3-second hold rate and click-through to ep 1. Feed the winners back as examples.
